# Nutri-flow 项目统一总计划（唯一保留版）

## 1. 项目定位

本项目是一个面向 C 端的移动应用：通过食物图像实例分割与热量估算，帮助用户快速了解一餐的大致热量与营养构成。

毕业设计核心：基于 Swin Transformer 的食物实例分割。

产品核心价值：把算法能力包装成可真实使用、可上线验证的移动端体验闭环。

范围边界：只聚焦热量分析相关健康管理，不扩展到医疗诊断。

## 2. 功能总览与优先级

### 2.1 核心功能（必须保留）

1. 用户目标设定
- 支持用户手动输入简短目标（例如：减脂、控制每日热量）。
- 支持 Agent 引导式问答生成目标画像（仅限热量相关问题）。

2. 餐食拍照与上传
- 支持拍照与相册上传。
- 上传后进入异步分析状态，并可查看任务进度。

3. 实例分割结果展示
- 返回分割可视化图。
- 每个分割实例可点击查看详情。

4. 食物详情与热量估算
- 每个实例展示：食物名称、估算热量、简要营养信息、食物简介。
- 页面展示本餐总热量。
- 所有数值明确标注“估算值”。

5. 历史记录
- 可查看历史分析记录与详情，支持回顾同类饮食模式。

### 2.2 增强功能（可选）

1. Agent 个性化提示
- 基于目标和近期记录给出简短建议。
- 提示内容必须围绕热量管理，不输出泛健康诊疗内容。

2. 结果解释增强
- 给出热量来源占比（主要贡献食物）。
- 给出区间估计与置信等级，帮助用户理解误差。

### 2.3 暂不纳入

1. 泛医疗建议与疾病诊断。
2. 复杂社交功能。
3. 长链路、开放域健康问答。

## 3. 用户流程设计（移动端）

1. 首次进入
- 二选一：手动输入目标 / Agent 问答生成目标。
- 结果统一落到同一份用户画像字段。

2. 主页面操作
- 拍照或上传餐食图片。
- 选择餐别并提交任务。

3. 分析处理中
- 轮询任务状态：PENDING、COMPLETED、FAILED、TIMEOUT。
- 任何异常都提供可理解提示和重试入口。

4. 结果查看
- 展示分割图与总热量。
- 点击任一实例查看该食物详情。

5. 保存与回看
- 自动写入历史记录。
- 用户可随时回看本次估算与建议。

## 4. Agent 交互边界与问题模板

### 4.1 交互边界

1. 只采集热量估算必要信息。
2. 不讨论治疗方案和医学诊断。
3. 问题数量控制在 3-5 个，避免用户流失。

### 4.2 推荐问题模板

1. 你的主要目标是减脂、维持，还是增肌？
2. 你日常活动量大概是低、中还是高？
3. 你是否有需要回避的食物类型？
4. 你更希望控制总热量，还是提升蛋白占比？
5. 你希望我给你偏严格还是偏宽松的热量提醒？

## 5. 技术闭环与架构要点

1. 链路结构
- 移动端上传图片。
- 业务后端创建任务并投递 MQ。
- AI 服务执行实例分割与热量估算。
- 结果回写后端，前端轮询获取并展示。

2. 必须保障的工程点
- taskId 全链路一致性。
- 状态机完整性（含超时与失败）。
- 结果字段与前端点击实例一一对应。

3. 低成本上线原则
- 以现有 Docker 化服务为主，先保证稳定可用。
- 模型能力优先用于核心链路，不做高成本扩展。

## 6. 结果页信息结构（建议定稿）

1. 第一层：总览
- 总热量（本餐估算）。
- 简短风险提示（例如：本餐热量偏高）。

2. 第二层：实例列表
- 每项显示缩略图、名称、热量。
- 点击可进入详情卡片。

3. 第三层：详情解释
- 营养简析（蛋白、脂肪、碳水的简要说明）。
- 食物简介与建议替代项。
- 置信说明与估算范围。

## 7. 异常与降级策略

1. 上传失败：给出重试与网络检查。
2. 超时：提示系统繁忙并支持再次提交。
3. 低置信度：显示“识别不稳定”标签并建议补拍。
4. 小类别不稳定：优先展示主要食物，避免误导。
5. 回写异常：前端不崩溃，保留任务号用于追踪。

## 8. 验收标准（答辩与上线通用）

1. 用户可独立完成一次完整分析。
2. 主流程成功率可观测且稳定。
3. 结果页可点击实例并读取正确详情。
4. 异常场景有明确反馈与恢复路径。
5. 建议文本与用户目标存在可解释关联。

## 9. 算法实验规划整合（原 Stage 计划合并）

### 9.1 总体方向

1. Stage6-C：热量估算闭环增强
- 建立类别到营养映射表。
- 校准估算区间与置信等级。
- 评估无尺度与带尺度先验两类方案。

2. Stage6-S：分割性能增强
- 以分辨率与训练策略为主变量。
- 采用 full-val 作为最终排序依据。
- 重点观察 mIoU 与非背景有效类别覆盖。

### 9.2 关键结论沉淀

1. 512 分辨率在多轮实验后表现出更高上限。
2. 长程训练存在后段回撤风险，需门控机制避免覆盖早期最优。
3. 训练期代理指标不能替代 full-val 结论。

### 9.3 后续实验策略（统一版）

1. 固定 512 为主线候选。
2. 采用分阶段训练与阶段性 full-val。
3. 每阶段基于 full-val 进行选优门控，再进入下一阶段。
4. 任何阶段若出现指标回落且覆盖下降，立即回滚到上一最佳 checkpoint。

## 10. 风险清单与对策

1. 模型精度与用户感知不一致
- 对策：强调估算属性，增强解释性，支持补拍与重试。

2. 异步链路中断导致长时间等待
- 对策：状态机严格化，超时兜底，日志按 taskId 贯穿。

3. 功能扩张导致主线不稳定
- 对策：冻结核心范围，附加功能只做轻量版本。

4. 上线成本超预算
- 对策：优先复用现有部署结构，控制并发与图片尺寸。

## 11. 对外口径（答辩可直接复用）

1. 这是一个“以实例分割为核心能力、以热量估算为用户价值”的移动端系统。
2. 价值不在精确到医学级诊断，而在“可用、可解释、可持续记录”的日常饮食管理。
3. 工程上完成了从模型到 C 端应用的闭环落地，并具备真实上线验证能力。
