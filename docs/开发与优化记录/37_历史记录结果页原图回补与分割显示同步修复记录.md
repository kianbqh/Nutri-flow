# 37 历史记录结果页原图回补与分割显示同步修复记录

## 1. 文档目的

本记录用于沉淀本轮历史记录详情页修复，重点说明：

1. 为什么历史记录中看到的分割结果会和拍照后直接展示的结果不一致。
2. 为什么历史记录详情里的图片预览会显示“图片预览不可用”。
3. 本轮如何通过原图回补把两条展示链路重新对齐。

## 2. 触发背景

用户反馈当前存在两个连在一起的问题：

1. 从拍照分析完成后直接进入结果页时，分割结果显示正常。
2. 从历史记录再次打开同一任务时，分割观感和刚分析完不一致。
3. 历史记录详情顶部的图片预览还会直接显示“图片预览不可用”。

这说明问题不在模型推理结果本身，而在历史详情页重新组装结果页时，缺了某个关键展示输入。

## 3. 根因定位

本轮沿着两条链路做了对比：

### 3.1 拍照后直达结果页链路

当前上传链路是：

1. `upload_page.dart` 读取选中图片字节 `_previewBytes`
2. `processing_page.dart` 在轮询完成后把 `imageBytes` 连同 `result` 一起传给 `ResultPage`
3. `result_page.dart` 因此既有分析结果，也有原始餐图字节

### 3.2 历史记录详情链路

当前历史链路原先是：

1. `history_page.dart` 只调用 `getTaskStatus(taskId)`
2. 随后直接 `ResultPage(result: result)`
3. 没有把原始餐图字节传入结果页

### 3.3 直接导致的两个表现

这会直接带来两个结果：

1. 顶部大图预览因为 `imageBytes == null`，只能显示“图片预览不可用”。
2. 交互分割画布因为拿不到原图，只能退化为使用 `segmentationPreviewPngBase64` 作为底图；而拍照后直达结果页时，画布会优先显示原图，因此两者视觉观感出现偏差。

也就是说，历史页和直达页拿到的是同一份分析结果，但并没有拿到同一份原图展示输入。

## 4. 修复思路

本轮没有去改结果页分割逻辑，而是直接补齐历史详情缺失的原图来源。

### 4.1 后端新增按任务取原图能力

为避免前端直接去碰 OSS 预签名 URL 带来的跨域、过期和稳定性问题，本轮在 business 服务新增：

1. `GET /api/v1/diet-logs/{taskId}/image`

实现方式为：

1. 通过 `taskId` 查到 `DietLog`
2. 使用数据库中已有的 `ossKey`
3. 由服务端通过 `OssService` 直接回源下载对象字节
4. 再把图片字节回传给移动端

这样历史详情页不需要自己处理 OSS 下载细节，只要按 taskId 取图即可。

### 4.2 移动端历史详情补齐原图回补

本轮在 `history_page.dart` 中做了两步调整：

1. 先拿历史任务的 `AnalysisResult`
2. 再调用新增的 `/diet-logs/{taskId}/image` 接口取回图片字节
3. 最终以 `ResultPage(imageBytes: imageBytes, result: result)` 的形式打开详情

这使得历史详情页终于能和拍照直达结果页一样，把“分析结果 + 原图字节”一并传入结果页。

### 4.3 结果页增加顶部预览兜底

为了避免未来极端情况下原图回补失败时顶部完全空白，本轮还在 `result_page.dart` 中补了一个兜底策略：

1. 优先显示原图 `imageBytes`
2. 若原图为空，则回退显示 `segmentationPreviewPngBase64`
3. 两者都不存在时，才显示“图片预览不可用”

这样可以减少结果页顶部出现空白态的概率。

## 7. 工程结论

这次问题的本质不是“历史记录用了另一套分割结果”，而是历史详情页没有把原图一并带回结果页，导致：

1. 顶部图片预览缺失
2. 分割画布只能退化为使用分割预览图做底图
3. 从而看起来和拍照后直达结果页不一致

本轮通过“后端按 taskId 回源取图 + 移动端历史详情补齐原图字节”的方式，已经把历史详情结果页重新拉回到和直达结果页一致的展示链路上。
