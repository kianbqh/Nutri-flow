# 16 分析链路性能优化记录

## 1. 文档目的

本记录用于沉淀本轮“上传图片后分析耗时过长”的定位与优化过程，便于后续论文撰写、答辩说明和工程复盘。

## 2. 问题背景

在本地联调阶段，用户上传图片后通常需要接近 100 秒才能拿到完整分析结果，且个别请求会出现 502 或长时间 pending。该问题既影响演示体验，也会放大移动端轮询等待的感知成本。

## 3. 优化目标

1. 优先消除链路中的不稳定点，而不是只做表面提速。
2. 在不明显牺牲识别和建议质量的前提下缩短总耗时。
3. 所有优化都必须能通过真实 smoke task 验证，而不是只靠局部推断。

## 4. 根因拆解

### 4.1 图片二次拉取带来的不稳定性

业务服务上传原图到对象存储后，会把预签名 URL 发给 agent，再由推理服务重新通过该 URL 拉图。这个二次网络依赖导致两类问题：

1. 预签名 URL 偶发拉取失败，直接引发 502。
2. 即使不失败，也增加了一次额外 I/O 和解码耗时。

### 4.2 分割模型首请求冷启动

推理模型在服务启动后第一次真正推理时才完成权重加载和图优化，导致首个任务明显慢于后续任务。

### 4.3 检索阶段串行执行

用户记忆检索和营养知识检索原本是串行执行，两段等待被直接叠加到完整工作流里。

### 4.4 建议生成模型选择不合适

最初 advice 节点使用 Moonshot 的 kimi-k2.6。实测表明，在当前提示词结构下，该模型虽然会消耗掉大量 completion tokens，但经常返回空的可见内容，导致：

1. 规则兜底被频繁触发。
2. 为了补救而增加重试后，整体耗时反而继续上升。

## 5. 优化思路

本次优化遵循“先去不稳定依赖，再处理慢节点，最后做模型选择”的顺序。

### 5.1 内联传递分析图，去掉二次取图依赖

在业务服务上传原图后，额外生成一张用于分析的压缩 JPEG 预览图，并以 Base64 的形式直接放入 MQ 任务消息。这样 agent 和推理服务优先消费内联图片字节，不再依赖二次访问对象存储。

相关实现位置：

1. nutri-business/src/main/java/com/nutriflow/controller/DietLogController.java
2. nutri-business/src/main/java/com/nutriflow/mq/ImageAnalysisTaskMessage.java
3. contracts/image_analysis_task.schema.json
4. nutri-agent/app/mq_consumer.py
5. nutri-ai-mcp/app/routers/inference.py

### 5.2 推理服务启动预热

在 FastAPI 服务启动阶段用一张 64x64 的 dummy image 主动跑一次推理，把模型加载和图初始化前置到启动时完成，避免首个真实请求承担冷启动成本。

相关实现位置：

1. nutri-ai-mcp/main.py

### 5.3 检索并行化

完整分析模式下，用户记忆和营养知识检索没有强依赖关系，因此改为在 graph 中并行执行，再统一合并 workflow trace 和上下文结果。

相关实现位置：

1. nutri-agent/app/graph.py

### 5.4 压缩 LLM 输入上下文

为避免 advice 节点在远端模型上浪费过多 token，本轮对用户记忆和 RAG 文本做了统一裁剪，同时保留规则兜底逻辑，确保即使外部模型不可用，也不会让任务直接失败。

相关实现位置：

1. nutri-agent/app/nodes/generate_advice.py

### 5.5 重新选择更适合当前任务的 Moonshot 模型

针对 advice 节点，单独对比了 kimi-k2.6 与 moonshot-v1-8k：

1. kimi-k2.6 在当前 ADVICE_PROMPT 下经常出现 finish_reason=length，但 response.content 为空。
2. moonshot-v1-8k 在同样提示词和同样 API key 下可以稳定返回可见中文建议。
3. moonshot-v1-8k 的 completion token 消耗明显更低，单次 advice 通常只需要 6 到 10 秒。

因此，最终将默认 Moonshot 模型切换为 moonshot-v1-8k。

相关实现位置：

1. nutri-agent/app/nodes/generate_advice.py
2. nutri-agent/.env

## 6. 关键实现步骤

### 6.1 业务服务侧

1. 上传原图后生成分析用缩略图。
2. 控制最长边为 1024，JPEG 质量约为 0.82。
3. 将 analysisImageBase64 随 MQ 消息一起发送。

### 6.2 Agent 与推理服务侧

1. Agent 消费任务消息时将 image_base64 写入 AgentState。
2. 调用分割服务时优先发送 image_base64。
3. 推理接口优先解码 image_base64，只有缺失时才回退到 image_url。
4. 对 URL 拉取保留有限次 retry，避免对象存储偶发波动直接中断任务。

### 6.3 Advice 节点侧

1. 裁剪用户记忆与知识库上下文。
2. 记录 advice 节点 elapsed_ms 进入 workflowTrace，方便前后对比。
3. 将模型从 kimi-k2.6 切换为 moonshot-v1-8k。
4. 保留规则兜底建议，确保 provider 不稳定时任务仍可闭环。

## 7. 验证方式

本次优化不是只做静态修改，而是通过以下方式逐步验证：

1. Python 侧模块导入与节点调用验证。
2. Java 业务服务编译验证。
3. dev-down -> dev-up -> dev-health，确认 consumer 数量恢复为 1。
4. 真实上传 smoke image，检查业务日志、推理日志和状态查询接口。

## 8. 最终效果

最终 smoke task：5067a1b8-e4c2-4acf-8a03-b0f9e560ce59

关键结果：

1. 任务状态为 COMPLETED。
2. workflowTrace 明确显示 generate_advice 成功调用 moonshot-v1-8k。
3. advice 节点 elapsed_ms 约为 9269 ms。
4. 整个任务从发布到回写数据库约为 13 到 14 秒。
5. 推理阶段 inference_time_ms 约为 11.41 ms。

与最初接近 100 秒的体验相比，链路耗时已显著下降，且链路稳定性明显提升。

## 9. 对论文撰写的可用表述

本次优化可在论文中总结为四类工程策略：

1. 数据传输链路优化：用内联分析图替代远程二次取图。
2. 模型服务可用性优化：通过启动预热削峰首请求冷启动。
3. 工作流并发优化：并行获取用户上下文与营养知识。
4. 模型适配优化：根据真实任务提示词选择更适合的生成模型，而不是只追求更强的通用模型名称。

## 10. 后续建议

1. 若后续要继续压缩整体耗时，可进一步将前端体验改为“分阶段返回”：先展示分割和热量，再异步补充长文本建议。
2. 若未来引入新的 LLM provider，应继续保留 task 级别的 elapsed_ms 记录，避免只凭主观感受判断快慢。
