# 49 网页端结果页历史详情与上传体验收口优化归档

## 1. 背景

本轮网页端优化不是单点修补，而是围绕“结果页像产品页而不是调试页”这一目标，对 `nutri-web` 做了一次连续收口。

在进入本轮之前，网页端主要存在以下问题：

1. 历史记录只能看到摘要，无法稳定进入详情页。
2. 结果详情页仍残留 `taskId`、workflow、实现说明等开发视角信息。
3. 分割图像存在“静态图和可点击区分裂”“看得到但点不动”“轮廓与图像略有偏移”等体验问题。
4. 检测食物名称仍可能暴露英文标签。
5. 识别明细按实例逐行展开，与移动端按类别归并的表达不一致。
6. 上传页把“选图、预览、餐次、开始分析”拆在较远位置，使用流程有割裂感。

因此，本轮目标不是继续堆界面元素，而是把网页端结果链路收成一个更稳定、更接近用户使用习惯的版本。

## 2. 本轮目标

本轮聚焦以下几项网页端体验约束：

1. 历史记录必须能进入结果详情。
2. 结果详情只保留用户关心的信息，不展示开发视角字段和实现说明。
3. 分割图像只保留一个可交互区域，并且必须真正可点击。
4. 食物名称统一显示中文。
5. 识别明细按食物类别归并显示。
6. 上传页把选图、预览、餐次和开始分析收拢到同一工作区附近。

## 3. 控制面判断

本轮首先确认了网页端结果体验的控制面主要集中在以下文件：

1. `nutri-web/src/stores/food.js` 控制任务详情加载、结果标准化与前端状态。
2. `nutri-web/src/api/dietLog.js` 控制历史详情页所需的图片与状态接口读取。
3. `nutri-web/src/components/MaskCanvas.vue` 控制分割图像的绘制、命中测试和图例交互。
4. `nutri-web/src/components/AnalysisResultPanel.vue` 控制结果页主体结构、摘要卡、识别明细和建议区。
5. `nutri-web/src/views/HistoryView.vue`、`nutri-web/src/views/TaskResultView.vue`、`nutri-web/src/router/index.js` 控制历史进入详情的前端链路。
6. `nutri-web/src/views/UploadView.vue` 控制上传工作区的布局和用户操作顺序。

因此，本轮采用的最小可行策略不是重写业务后端，而是：

1. 修正结果数据源与详情拉取方式。
2. 重写分割交互区和结果面板结构。
3. 清理页面上所有开发视角文案。
4. 按用户操作路径重排上传页工作区。

## 4. 具体改动

### 4.1 历史记录进入详情链路补齐

在 `HistoryView.vue`、`TaskResultView.vue` 和路由层完成：

1. 新增 `/results/:taskId` 详情页路由。
2. 历史卡片点击后进入结果详情页。
3. 详情页进入后自动拉取该任务的原图和完整分析结果。

这一步解决了“历史记录点不进去”以及“历史详情没有原图和完整结果”的问题。

### 4.2 结果数据源修正

在 `food.js` 中确认并修正了一个关键事实：

1. 业务状态接口里真正带 `mask_rle` 和 `mask_shape` 的数据源是 `detected_instances`。
2. 旧版网页端优先读取 `detected_items`，导致前端只能退化成静态预览，无法恢复可点击分割。
3. 修正后改为优先读取 `detected_instances`，仅在缺失时再回退到 `detected_items`。

这一步是“分割图像看起来有内容但实际点不动”的根修复。

### 4.3 历史详情原图回补

在 `dietLog.js` 和 `food.js` 中完成：

1. 增加 `getTaskImageBlob(taskId)` 能力。
2. 在详情页加载任务时，额外请求 `/diet-logs/{taskId}/image` 回补原图。
3. 原图使用 blob URL 挂到结果页，避免历史详情只剩分割预览图。

这一步让历史详情与上传后即时结果页都能展示原图。

### 4.4 分割交互区重构

在 `MaskCanvas.vue` 中完成了较大改造：

1. 支持按类别聚合实例，并生成单一交互图例。
2. 支持 RLE 掩码解码、聚合掩码合并、轮廓绘制和命中测试。
3. 结果区只保留一个分割交互区域，不再拆成“静态分割图”和“可点击区域”两块。
4. 后续又修正了 overlay 坐标系，改为以完整 mask 空间为基准绘制，而不是缩进到原图 contain 后的矩形里。

这一步解决了：

1. 分割区分裂。
2. 点击无响应。
3. 轮廓略小于原图内容。

### 4.5 结果页结构收口

在 `AnalysisResultPanel.vue` 中完成：

1. 删除 `taskId`、workflow、复制任务号等开发功能残留。
2. 顶部保留结果图、总热量、状态和摘要卡，不再出现开发字段。
3. 结果页只保留用户关心的四块内容：分割图像、识别明细、饮食建议、返回操作。
4. 识别明细改为按食物类别分组汇总，而不是按单个实例逐行展开。

同时，本轮还清理了结果页上“与 app 端一致”“不再拆成两个区域”“自动合并显示”等解释实现方式的文案，改成了纯用户视角提示。

### 4.6 中文食物名称统一

在 `foodLabels.js` 中新增并统一了网页端中文标签映射：

1. 增加 `FOOD_LABEL_ZH`。
2. 增加 `resolveFoodLabel(item)`。
3. 增加 `buildFoodGroupKey(item)`。

这一步让网页端结果页、图例和识别明细不再暴露英文类别名。

### 4.7 上传页工作区重排

在 `UploadView.vue` 中完成：

1. 把“选图、预览、餐次、开始分析”从分散位置收拢为同一块上传工作区。
2. 左侧承载选图与图片预览，右侧紧邻餐次、按钮和状态信息。
3. 删除“本页流程”“轮询”“放在同一块区域”这类讲实现方式的文案。
4. 保留与用户直接相关的提示，例如拍摄建议、当前状态、结果说明和开始前确认。

这一步主要解决上传页的操作割裂感，以及页面文案开发味过重的问题。

## 6. 验证

本轮不是只做静态代码修改，而是完成了多轮构建和浏览器验证：

1. 多次执行 `nutri-web` 的 `npm run build`，确认页面重构和结果面板改造未引入构建错误。
2. 在浏览器中验证历史页能够进入 `/results/:taskId`。
3. 在真实结果页中验证分割图像只保留一个交互区域。
4. 在真实结果页中直接点击 canvas，确认能选中食物并显示详情卡。
5. 在结果详情页中验证任务号、workflow 和开发说明文案已经移除。
6. 在识别明细中验证类别汇总逻辑生效，不再按实例逐行展开。

## 7. 当前收口后的长期约束

后续继续改网页端时，应保留以下约束，不要回退：

1. 结果页不展示 `taskId`、workflow、接口字段名、实现说明和对齐说明。
2. 分割结果只保留一个交互区，不再拆成静态图和点击区两段结构。
3. 分割交互优先依赖 `detected_instances`，不要回到 `detected_items` 优先。
4. 食物名称统一显示中文。
5. 识别明细按食物类别汇总，不按单个实例逐行展开。
6. 上传页首屏应优先服务“选图 -> 看图 -> 选餐次 -> 开始分析”这一连续操作。

## 8. 结论

本轮网页端优化的价值，不只是让页面“更像移动端”，而是把网页端从一个可联调用的原型结果页，收成了一个更接近正式产品体验的版本：

1. 历史记录和结果详情链路完整可用。
2. 分割交互区真正可点击且坐标对齐稳定。
3. 结果展示开始回到用户视角，不再掺杂开发解释。
4. 上传页主流程更贴近真实使用习惯。

这份记录可作为后续继续做网页端视觉润色、建议区信息压缩和多端一致性微调时的直接背景材料。
