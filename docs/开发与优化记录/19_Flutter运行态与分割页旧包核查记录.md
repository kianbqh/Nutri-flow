# 19 Flutter 运行态与分割页旧包核查记录

## 1. 文档目的

本记录用于说明一次非常典型的联调问题：代码已经修改，但用户界面看起来几乎没有变化。该文档重点沉淀如何区分“代码没写对”和“前端仍在运行旧包”这两类问题。

## 2. 问题现象

在完成分割结果页的多轮优化后，用户仍反馈“分割图像还是和之前一样”。从截图上看，存在两个异常信号：

1. 结果页仍然显示大面积橙色选中填充。
2. 页面中直接展示了分类详情卡，表现得像默认已经选中了第一个分割区域。

## 3. 代码侧核查

对当前结果页代码核查后，确认现有逻辑并不会在初始化阶段默认选中第一个区域：

1. `_selectedGroup` 只在点击命中 `_handleTap` 时赋值。
2. `initState()` 中已经没有 `_selectedGroup = _overlayGroups.first` 之类的默认选中逻辑。
3. 新版页面文案中还加入了“默认显示原图和轻量轮廓”的提示。

因此，如果截图中仍然表现为“默认已选中”，那就说明用户当前看到的页面大概率并不是这份最新代码构建出来的运行结果。

## 4. 运行态核查

进一步检查本机 Flutter 进程后，发现当前机器上存在一个持续运行的 web-server 进程，命令为：

1. `flutter run -d web-server --web-hostname 127.0.0.1 --web-port 57717`

这说明当前测试页面很可能仍然来自一个较早启动的 Flutter web 调试包，而不是刚刚修改后的最新构建。

## 5. 根因判断

本次问题的高概率根因是：

1. 结果页代码已经更新。
2. 但当前正在访问的 Flutter web 运行实例没有完成热重启或重新启动。
3. 因此浏览器里展示的仍然是旧前端包。

## 6. 处理动作

本轮采取的处理方式是直接面向运行态，而不是继续怀疑结果页代码：

1. 记录本次问题定位过程。
2. 重启当前 Flutter web-server，使其重新编译并加载最新代码。
3. 建议在浏览器中执行一次强制刷新，避免前端资源缓存继续命中旧 bundle。

## 7. 工程结论

这次问题能够说明一个很重要的工程经验：

1. UI 看起来“没有变化”时，不能只盯着代码 diff。
2. 运行态、调试包、浏览器缓存和热重载状态同样会直接影响用户观感。
3. 在 Flutter 联调场景下，需要同时核对“代码逻辑”和“当前运行实例是否已经重启”。

## 8. 后续建议

1. 如果后续继续通过 web-server 方式调试，建议每次涉及结果页结构变化后执行一次 hot restart，而不是只依赖 hot reload。
2. 如果页面表现与代码逻辑明显不符，应优先检查当前设备或浏览器是否仍连接到旧 Flutter 调试实例。
