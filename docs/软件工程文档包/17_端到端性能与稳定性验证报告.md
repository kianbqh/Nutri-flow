# Nutri-flow 手动测试、端到端性能与稳定性验证报告

版本：v1.0

## 1. 文档目的

本文档用于沉淀当前 0.1 阶段已完成的手动测试、链路性能与稳定性验证结论，服务于以下场景：

1. 证明系统已具备基本联调、手动测试与答辩演示能力。
2. 为毕业论文中的“系统手动测试与运行验证”章节提供事实依据。
3. 为后续补录截图、测试执行表和发布检查提供最小自检基线。

## 2. 验证范围

本轮验证覆盖以下范围：

1. 本地/近线环境下的后端链路启动与健康检查。
2. 移动端与网页端主流程手动测试。
3. 关键异常场景手动测试。
4. 真实近线冒烟任务的端到端完成时延。
5. RabbitMQ 单消费者约束。
6. 网页前端生产构建可用性。
7. 受管脚本对 orphan 进程与重启行为的恢复能力。

## 3. 目标与通过标准

### 3.1 当前验证策略

当前阶段采用“手动测试 + 运行验证”策略。复杂自动化测试并非本轮重点，原因在于当前需要优先完成以下工作：

1. 证明移动端与网页端主流程已经可用。
2. 证明关键异常路径具备可恢复动作。
3. 证明后端链路、任务状态和近线性能达到答辩展示要求。

### 3.2 已定义的目标

根据需求规格说明书，当前可直接对照的非功能目标包括：

1. 分析平均时延目标：`15` 秒以内。
2. 基础并发下稳定处理，不出现任务丢失。
3. `taskId` 必须可追踪，状态不能长期卡死在 `PENDING`。

### 3.3 当前验证通过标准

当前项目将以下结果视为最小通过线：

1. P0 手动测试用例全部达到预期。
2. P1 手动测试用例整体达到预期。
3. 无阻断级缺陷。
4. 健康检查脚本五项检查全部为 OK。
5. RabbitMQ 任务队列消费者数量为 1。
6. 近线冒烟任务能从创建推进到完成状态。
7. 网页端生产构建可成功输出产物。

## 5. 本轮稳定性治理结论

### 5.1 受管脚本与 supervisor 机制

当前本地运行态已采用以下治理手段：

1. 后端服务统一通过 `.runtime/supervisors/*.ps1` 托管。
2. `dev-up / dev-health / dev-down` 形成统一启动、巡检、关闭路径。
3. `dev-down` 不仅关闭 pid 文件对应的 supervisor，也会额外清理 `nutri-agent` 孤儿进程以及 8001/8080 监听进程。

### 5.2 推理服务预热结论

已确认一个重要运行事实：

1. `scripts/dev-restart-all.ps1 -SkipDocker` 在推理服务冷启动时，可能因为模型预热出现短暂健康检查失败。
2. 此时不能直接判定服务损坏，应在预热完成后重新执行 `scripts/dev-health.ps1`。
3. 只要健康检查回绿，说明问题属于启动窗口，而不是稳定性故障。

### 5.3 RabbitMQ 单消费者恢复结论

本轮 0.1 发布前检查中，曾发现 task queue 的消费者数异常升至 `7`。排查与处理结果如下：

1. 根因是旧版受管 agent 使用相对路径启动 `main.py`，导致孤儿 Python 进程无法被 `dev-down` 稳定识别。
2. 本轮已修复 `scripts/dev-up.ps1`，改为使用绝对路径启动 `nutri-agent/main.py`。
3. 本轮已修复 `scripts/dev-down.ps1`，兼容清理历史遗留的旧命令行格式。
4. 修复后执行 `dev-down -> dev-up -SkipDocker -> dev-health`，RabbitMQ task consumer 已恢复为 `1`。

该问题已从“潜在误处理风险”收敛为“已修复并验证通过”的发布前缺陷。

## 6. 当前性能判断

### 6.1 与目标对照

1. 需求目标为平均时延 `15` 秒以内。
2. 当前已验证的近线冒烟任务总耗时约为 `13` 到 `14` 秒。
3. 因此本地/近线环境下的主链路已达到当前性能目标。

### 6.2 当前瓶颈判断

1. 推理阶段仅约 `11.41 ms`，不是主要瓶颈。
2. 建议生成节点约 `9269 ms`，是当前体验上的主要耗时来源。
3. 若后续继续优化整体体验，优先级应放在 advice 链路而非分割推理。

在当前本地/近线环境下，可以给出如下结论：

1. 仓库处于可继续发布整理的健康状态。
2. 移动端与网页端主流程手动测试结果整体良好。
3. 网页前端生产构建通过。
4. 后端链路经受管脚本重拉后恢复正常。
5. RabbitMQ 任务队列已回到单消费者健康状态。
6. 当前剩余工作重点已从“修复稳定性故障”转为“补录截图表格与准备答辩展示”。

## 8. 剩余风险与后续建议

1. 当前验证结论主要针对本地/近线环境，不等同于公网部署完成。
2. 当前测试仍以手动测试为主，复杂自动化测试能力尚未建设。
3. 推理服务冷启动依旧存在预热窗口，应在运维文档中保留此说明。
4. 发布前仍建议保留单消费者作为健康基线，避免旧进程误消费任务。
5. 若未来引入更多 worker 或并发消费者，应同步重写健康检查与幂等策略，不应直接沿用当前单消费者假设。
