# Nutri-flow 系统架构设计文档

版本：v1.0

## 1. 设计目标

1. 支撑移动端“上传-分析-展示”完整闭环。
2. 通过异步架构降低前端阻塞。
3. 保障模型服务可独立迭代与部署。
4. 兼顾低成本上线与可观测性。

## 2. 总体架构

系统采用多服务协同架构：

1. 移动端（Flutter）：用户交互与状态展示。
2. 业务后端（Spring Boot）：API 网关、任务持久化、消息投递与结果回写。
3. 消息中间件（RabbitMQ）：解耦上传请求与推理执行。
4. Agent 服务（Python/LangGraph）：编排用户上下文、推理调用、建议生成。
5. AI 推理服务（FastAPI + MCP）：实例分割与营养估算。
6. 对象存储（MinIO/OSS）：原始图片与中间结果存储。
7. 数据存储（MySQL/Redis/Chroma 可选）：业务数据、缓存与知识检索。

## 3. 核心时序

### 3.1 主链路

1. 客户端调用上传接口，携带 mealType 与用户标识。
2. 后端保存元信息、上传图片、生成 taskId。
3. 后端按契约投递 MQ 任务。
4. Agent 消费任务并调用 AI 推理服务。
5. 推理结果与建议生成后回传后端。
6. 前端轮询状态，完成后展示分割与热量结果。

### 3.2 异常链路

1. 上传异常：接口直接返回错误，前端提示重试。
2. 推理失败：任务状态置 FAILED，前端可重新提交。
3. 轮询超时：前端置 TIMEOUT，保留 taskId 供追踪。

## 4. 模块设计

### 4.1 移动端模块

1. 页面模块：Capture、Processing、Result、Profile、History。
2. 网络模块：API Client + Error Model。
3. 状态模块：任务状态机与轮询控制器。
4. 渲染模块：分割图层与实例交互。

### 4.2 后端模块

1. 用户模块：用户画像读写。
2. 饮食日志模块：任务创建、状态查询、历史分页。
3. MQ 模块：生产者与结果消费者。
4. 存储模块：OSS 对象管理。

### 4.3 Agent 模块

1. 任务入口：消费分析任务。
2. 推理调用：MCP 协议调用分割服务。
3. 上下文增强：读取 userContext。
4. 建议生成：限定在热量管理范围。
5. 结果发布：回传回调队列。

### 4.4 AI 模型模块

1. 预处理：图像标准化。
2. 推理：Swin Transformer + BiFPN + Coordinate Attention。
3. 后处理：实例信息提取、热量估算、结果序列化。

## 5. 架构视图

### 5.1 逻辑视图

- Client 层：nutri-mobile
- Service 层：nutri-business、nutri-agent、nutri-ai-mcp
- Infra 层：RabbitMQ、MySQL、MinIO

### 5.2 部署视图（低成本）

1. 单机/单云主机 Docker Compose 部署基础依赖。
2. Java 与 Python 服务可同机分进程部署。
3. GPU 环境优先给推理服务；无 GPU 时降级并提示时延上升。

## 6. 关键设计决策

1. 异步优先：避免移动端长时间同步等待。
2. taskId 贯穿：便于追踪与故障定位。
3. 结果可解释：实例可点击查看，降低黑盒感。
4. 领域收敛：不扩展至医疗诊断。

## 7. 可观测性与运维

1. 日志规范：按 taskId 关联日志。
2. 指标建议：任务成功率、平均时延、P95 时延、失败率。
3. 告警建议：队列堆积、失败率突增、状态长时间停留 PENDING。

## 8. 安全与合规

1. 敏感信息最小化存储。
2. API 鉴权和输入校验。
3. 输出增加免责声明（估算值、非医疗建议）。
