# Nutri-flow 技术选型报告

版本：v1.0

## 1. 选型目标

1. 满足毕业设计核心：Swin 实例分割能力可落地到 C 端。
2. 满足工程目标：移动端可用、后端稳定、异步可扩展。
3. 满足成本目标：尽量低成本上线和维护。

## 2. 技术栈总览

1. 客户端：Flutter（nutri-mobile）
2. 业务后端：Spring Boot（nutri-business）
3. AI 编排：Python + LangGraph（nutri-agent）
4. 推理服务：FastAPI + MCP（nutri-ai-mcp）
5. 消息队列：RabbitMQ
6. 数据存储：MySQL
7. 对象存储：MinIO（可替换云 OSS）
8. 容器化：Docker Compose

## 3. 分模块选型分析

### 3.1 移动端：Flutter

选择原因：

1. 单代码库覆盖 iOS/Android。
2. UI 开发效率高，适合 MVP 快速迭代。
3. 便于后续 TestFlight 分发。

备选方案：原生 iOS / React Native。  
不选原因：开发维护成本更高或现有项目上下文不匹配。

### 3.2 业务后端：Spring Boot

选择原因：

1. 企业级生态成熟，接口与数据层稳定。
2. 与 MQ、数据库、中间件集成成本低。
3. 适合任务管理与状态机实现。

### 3.3 AI 编排：LangGraph + Python

选择原因：

1. 适合构建有状态的流程编排。
2. 便于将用户画像、RAG、推理调用串联。
3. 与 AI 生态和实验代码协同方便。

### 3.4 推理服务：FastAPI + MCP

选择原因：

1. Python 对模型推理支持友好。
2. FastAPI 性能与开发效率平衡较好。
3. MCP 便于标准化工具调用。

### 3.5 消息队列：RabbitMQ

选择原因：

1. 将上传请求与推理执行解耦。
2. 便于缓冲峰值流量。
3. 支持可靠投递与消费确认机制。

### 3.6 数据与存储：MySQL + MinIO

选择原因：

1. MySQL 适合结构化业务数据。
2. MinIO 便于本地和低成本部署。
3. 后续可平滑替换到云对象存储。

## 4. 模型方案选型

### 4.1 主模型

- Swin Transformer + BiFPN + Coordinate Attention

选择原因：

1. 对复杂场景分割表现更稳。
2. 具备较强论文与工程结合价值。
3. 与毕业课题高度一致。

### 4.2 训练与评估策略

1. 采用 full-val 作为关键决策指标。
2. 使用阶段门控避免长程训练回撤覆盖最优点。
3. 512 分辨率作为主线候选。

## 5. 成本与风险评估

### 5.1 成本

1. 研发成本：多服务协同复杂度较高。
2. 运行成本：推理服务对算力敏感。
3. 运维成本：需维护 MQ、DB、对象存储。

### 5.2 风险

1. 高峰期推理时延增加。
2. 模型误差导致用户理解偏差。
3. 异步链路异常导致任务状态不一致。

### 5.3 对策

1. 前端明确进度和重试策略。
2. 结果页强调估算属性与置信说明。
3. 全链路以 taskId 可观测。

## 6. 上线建议

1. 先以小规模内测（TestFlight）验证主流程稳定性。
2. 控制并发与图像尺寸，优先保证可用性。
3. 先稳住 P0，再逐步开启增强功能。

## 7. 结论

当前选型能较好平衡“课题创新性、工程可落地性、上线可行性”三者关系。建议保持现有技术主干不变，后续优化重点放在稳定性、可解释性和用户体验闭环。
